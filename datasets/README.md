# Datasets

This folder holds the data used by the CodeMind AI evaluation. Every number reported in the project documents comes
from one of the files below, run through `run_benchmark.py` (or `evaluation/benchmark_runner.py`).

| File | What it is | Size | Licence | Used for |
|---|---|---|---|---|
| `benchmark.json` | Custom Python bug benchmark, generated by `build_dataset.py` | 122 programs (30 dev, 92 eval) | MIT (written for this project) | Main three-way evaluation |
| `sample_bugs.json` | 12 small demo programs (S01 to S12) | 12 | MIT (written for this project) | "Load sample" buttons in the app, demos |
| `external/quixbugs.json` | QuixBugs Python programs converted by `prepare_quixbugs.py` | not created yet | MIT (QuixBugs) | Optional external check (`--split external`) |

## 1. Custom benchmark (`benchmark.json`)

Each example is a small single-function program with one injected bug. All programs, reference fixes, explanations and
test calls are written by hand in `build_dataset.py`. Nothing is copied from another dataset.

**Categories (122 examples):** logical_error 43, potential_runtime_error 13, undefined_variable 11, type_issue 11,
syntax_error 10, bad_practice 9, indentation_error 8, missing_import 8, unreachable_code 5, unused_variable 4.
**Difficulty:** easy 38, medium 69, hard 15.

**Fields per example:** `id`, `split`, `category`, `difficulty`, `intended_behavior`, `buggy_code`, `fixed_code`,
`bug_lines`, `validation_tests`, `heldout_tests`, `expected_output`, `error_explanation`.

### How it is built and verified

```
python datasets/build_dataset.py        # or: python -m datasets.build_dataset
```

The builder:

1. runs the **reference fix** (trusted code written for this project) in a subprocess with a timeout to compute the
   expected value of every test call;
2. checks that the reference passes every test and that the buggy version fails at least one test or does not parse,
   so every bug is observable. An example that fails this check stops the build;
3. derives `bug_lines` from a `difflib` diff of buggy vs fixed code;
4. assigns the split deterministically: every 4th example is `dev`, the rest are `eval`;
5. splits each example's tests into `validation_tests` and `heldout_tests`. Every example has at least 2 tests and the
   two sets never share a test call.

### Split and test policy (leakage control)

- **dev (30):** may be used to tune prompts and settings. Never reported as a result.
- **eval (92):** used only for the reported numbers. Do not look at eval failures while tuning prompts.
- **validation_tests:** shown to the repair loop (the hybrid mode may run them in the sandbox to check a fix).
- **heldout_tests:** never shown to any method; used only for scoring repairs. This stops a method from "passing"
  by overfitting to the tests it saw. `tests/test_evaluation.py` checks that the two sets do not overlap.

## 2. Demo samples (`sample_bugs.json`)

Twelve short programs (one per common bug type) for demos and the app's sample loader. They are not part of the
benchmark and are never used for reported results.

## 3. QuixBugs (optional, external)

QuixBugs: Lin, D., Koppel, J., Chen, A., and Solar-Lezama, A. "QuixBugs: A Multi-Lingual Program Repair Benchmark
Set Based on the Quixey Challenge." *Proceedings of SPLASH Companion 2017.* Repository:
<https://github.com/jkoppel/QuixBugs> (MIT licence).

```
python datasets/prepare_quixbugs.py     # writes datasets/external/quixbugs.json (needs internet)
python run_benchmark.py --split external --dataset datasets/external/quixbugs.json
```

Only programs with JSON test cases are converted; graph programs that need custom fixtures are skipped. All QuixBugs
examples get `split = "external"` so they never mix with the custom dev/eval splits. Results on QuixBugs are written to
`summary_trial.json` and do not replace the main results.

**Status:** the script exists but has **not been run yet** (the download was blocked in the development environment).
Run it on a machine with normal internet access before reporting any QuixBugs number.

## 4. BugsInPy (not used)

BugsInPy (Widyasari et al., ESEC/FSE 2020, <https://github.com/soarsmu/BugsInPy>) contains real bugs from large Python
projects. Each bug needs the full project, its dependencies and its own test suite, which does not fit the
single-file, offline design of CodeMind AI. It is mentioned in the report as related work and future scope only.

## Adding your own examples

Add a new `ex(...)` call in `build_dataset.py` (category, difficulty, intended behaviour, buggy code, fix, at least 2
test calls, explanation),
then rebuild. The build fails if the buggy code passes all tests or the fix fails one. Adding examples changes the
split assignment of later examples, so re-run every method after rebuilding and never mix results from two dataset
versions.
